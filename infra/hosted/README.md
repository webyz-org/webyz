# Hosted Webyz (webyz.io)

How the hosted product runs, layered on the open-source stack in `infra/`
without changing it. If you are self-hosting Webyz, this directory is not for
you: read `docs/self-hosting.md`.

## Shape

| Hostname | Container | What |
| --- | --- | --- |
| `webyz.io` | `webyz-web:3000` | marketing site, `apps/web` |
| `app.webyz.io` | `webyz-app:8080` | dashboard, built with the API origin baked in |
| `api.webyz.io` | `webyz-api:3042` | API, tracker script, ingest, Paddle webhooks |

Cloudflare fronts all three. The host's shared `nginx-proxy` container
terminates TLS (Let's Encrypt via its certbot webroot and daily renewal cron)
and reaches each container by name over the external `proxy` network. No host
ports are published. Postgres, ClickHouse and Redis are this stack's own, on
its `internal` network, with named volumes under Docker's data root
(`/home/docker` on this host).

Files:

- `docker-compose.hosted.yml`: the overlay. Split-host URLs for the API, the
  dashboard build args, the marketing service, the `proxy` network.
- `environment.example`: every setting; the real `environment` lives only on
  the server.
- `nginx/webyz.conf`: the three server blocks; `nginx/webyz.bootstrap.conf`
  for before certificates exist; `nginx/cloudflare-real-ip.conf` so
  `$remote_addr` is the visitor, regenerated by `nginx/update-cloudflare-ips.sh`.
- `certs.sh`: first issuance. `deploy.sh`: build, dump Postgres, migrate,
  start. `backup.sh`: the nightly backup (below). `clickhouse/backups.xml`:
  the ClickHouse backup disk the overlay mounts.

## First deployment

On the server, as the user that runs the other apps:

```sh
cd ~/apps/webyz && git pull
# Secrets generated straight into the file, never shown on a terminal.
PG=$(openssl rand -hex 24); CH=$(openssl rand -hex 24); EK=$(openssl rand -hex 32)
sed -e "s|^POSTGRES_PASSWORD=$|POSTGRES_PASSWORD=$PG|" \
    -e "s|^CLICKHOUSE_PASSWORD=$|CLICKHOUSE_PASSWORD=$CH|" \
    -e "s|^ENCRYPTION_KEY=$|ENCRYPTION_KEY=$EK|" \
    infra/hosted/environment.example > infra/hosted/environment
chmod 600 infra/hosted/environment
$EDITOR infra/hosted/environment       # integration keys, when you have them

cp infra/hosted/nginx/cloudflare-real-ip.conf ~/apps/nginx/conf.d/
cp infra/hosted/nginx/webyz.bootstrap.conf ~/apps/nginx/conf.d/webyz.conf
docker exec nginx-proxy nginx -t && docker exec nginx-proxy nginx -s reload
./infra/hosted/certs.sh you@webyz.io
cp infra/hosted/nginx/webyz.conf ~/apps/nginx/conf.d/webyz.conf
docker exec nginx-proxy nginx -t && docker exec nginx-proxy nginx -s reload

./infra/hosted/deploy.sh
```

Then set Cloudflare's SSL mode to Full (strict).

## Every later release

```sh
cd ~/apps/webyz && git pull && ./infra/hosted/deploy.sh
```

## Checks after a deploy

- `curl -s https://api.webyz.io/health/ready` answers 200.
- A tracker hit from a test page appears in the dashboard with a real country:
  that proves the Cloudflare real-IP chain, which the visitor hash, geo, rate
  limits and the Paddle IP allowlist all depend on.
- `docker compose ... logs api | grep cron:` lists the jobs.

## Backups

Nothing backs up on its own. `backup.sh` dumps Postgres (accounts, sites,
subscriptions, usage ledger, charging checkpoints) with `pg_dump` and
snapshots ClickHouse with its own `BACKUP DATABASE` onto the `backups` disk,
online, so it runs against the live stack with no downtime and no lost
events. Files go to `BACKUP_DIR`, are deleted after `BACKUP_KEEP_DAYS`, and
are copied to the rclone remote in `BACKUP_REMOTE` when one is set. All three
come from `environment`. Until `BACKUP_REMOTE` is set the backups live on
the same machine as the databases: fine against a bad migration or a mistaken
delete, useless against losing the host. Set it.

Install the nightly run once, as the deploying user:

```sh
mkdir -p "$(grep ^BACKUP_DIR= infra/hosted/environment | cut -d= -f2-)"
( crontab -l 2>/dev/null; echo '0 3 * * * cd ~/apps/webyz && ./infra/hosted/backup.sh >> "$HOME/backups/webyz/backup.log" 2>&1' ) | crontab -
./infra/hosted/backup.sh          # run one now
./infra/hosted/backup.sh --list   # every backup with an integrity check
```

`deploy.sh` also takes a Postgres-only dump tagged `predeploy` right before
`up`, because migrations are forward-only. The one thing a backup is for is
the restore, so do this once on a scratch machine before it is needed:

```sh
C="docker compose -f infra/docker-compose.yml -f infra/hosted/docker-compose.hosted.yml --env-file infra/hosted/environment"
$C stop api
# Postgres: load the dump over the running database (--clean drops first).
gunzip -c ~/backups/webyz/webyz-pg-nightly-<stamp>.sql.gz | $C exec -T postgres psql -U webyz webyz
# ClickHouse: put the archive on the backups disk, drop, restore, tidy.
$C cp ~/backups/webyz/webyz-ch-nightly-<stamp>.zip clickhouse:/backups/restore.zip
$C exec -T clickhouse sh -c 'clickhouse-client --password "$CLICKHOUSE_PASSWORD" -q "DROP DATABASE webyz_analytics"'
$C exec -T clickhouse sh -c "clickhouse-client --password \"\$CLICKHOUSE_PASSWORD\" -q \"RESTORE DATABASE webyz_analytics FROM Disk('backups', 'restore.zip')\""
$C exec -T clickhouse rm /backups/restore.zip
$C start api
```

Restore onto the same Webyz version the backup came from, then `deploy.sh`
to migrate forward if needed.

## Paddle, when live

With the live keys in `environment`: `npx tsx scripts/paddle/setup.ts
--webhook https://api.webyz.io/api/v1/paddle/webhook` (inside the API
container or from a machine with the same `DATABASE_URL`), then the secret via
`sync-webhook-secret.ts` or by hand. Default payment link
`https://app.webyz.io/settings/billing`; conversion off; tax excludes; Retain
never cancels. `apps/api/docs/billing-runbook.md` section 1a is the checklist.
